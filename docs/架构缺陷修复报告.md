## 修复概览

## ✅ 已修复的问题

### 1. 🟠 AgentPool 子智能体使用全局记忆单例（问题 6）

**问题描述：**
`AgentPool.runTask()` 中使用 `getMemoryStack()` 全局单例，导致 Gateway 多会话场景下，不同用户的子智能体共享同一份 L0/L1 记忆上下文，存在数据隔离漏洞。

**修复方案：**
- `TeamManager` 构造函数新增 `sessionId` 参数，绑定会话 ID
- `AgentPool.submit()` 新增 `parentSessionId` 参数，传递父会话 ID
- `runTask()` 中优先使用 `getMemoryStackForSession(parentSessionId)`，降级到全局单例
- 为子智能体生成独立的 `subSessionId`，通过 `runWithSession()` 隔离 todo 等工具状态

**影响文件：**
- `src/core/coordinator/AgentPool.ts`
- `src/core/coordinator/TeamManager.ts`

**验证方法：**
```bash
# Gateway 多会话场景下，不同用户的 team_submit 子智能体将继承各自会话的记忆
hrids-agent --gateway
# 前端创建两个会话，分别调用 team_submit，观察子智能体的记忆上下文
```

### 2. 🟠 PermissionManager 并发写入竞争（问题 5）

**问题描述：**
多个 Gateway 会话同时调用 `approvePermanent()` 时，存在 read-modify-write 竞争：
```typescript
// 旧：两个会话同时读到旧状态，都 push，最后一个写入覆盖另一个
if (!this.rules.alwaysAllow.includes(rule)) {
  this.rules.alwaysAllow.push(rule)
  saveRules(this.rules)
}
```

**修复方案：**
采用 **read-then-write** 模式：每次写入前重新从磁盘读取最新状态，合并后再写入。
```typescript
// 新：每次写入前重新读取，防止覆盖其他会话的修改
const fresh = loadRules()
if (!fresh.alwaysAllow.includes(rule)) {
  fresh.alwaysAllow.push(rule)
  saveRules(fresh)
}
this.rules = fresh  // 同步内存副本
```

**影响文件：**
- `src/core/PermissionManager.ts`（所有 `*Permanent()` 和 `*Path()` 方法）

**注意：**
这不是完美的分布式锁，仍然存在极小概率的竞争窗口（两个会话在同一毫秒内读取），但已大幅降低冲突概率。完美方案需要文件锁或数据库事务。

### 3. 🟠 autoDistillSkill 无并发写保护（问题 7）

**问题描述：**
多个并发会话同时提炼同名 skill 时，`writeFileSync()` 非原子，可能导致文件损坏。

**修复方案：**
使用原子写入模式（tmp + rename）：
```typescript
const tmpPath = skillMdPath + '.tmp'
writeFileSync(tmpPath, content, 'utf-8')
renameSync(tmpPath, skillMdPath)
```

**影响文件：**
- `src/core/postRunHooks.ts`

### 4. 🟡 FallbackProvider 并发状态修改（问题 8）

**问题描述：**
成功后分步修改共享实例状态，存在理论上的中间状态可见性问题：
```typescript
this.currentGroupIdx = localGroupIdx  // 第一步
this.currentModelIdx = localModelIdx  // 第二步（中间状态）
```

**修复方案：**
使用解构赋值原子更新（语义上的原子操作）：
```typescript
;[this.currentGroupIdx, this.currentModelIdx] = [localGroupIdx, localModelIdx]
```

同时移除未使用的 `_advanceLock` 字段。

**影响文件：**
- `src/core/providers/FallbackProvider.ts`

**注意：**
JS 单线程环境下两次赋值之间不会被抢占，但合并为单次赋值在语义上更清晰。

### 5. 🟡 ContextBuilder 缓存淘汰策略非 LRU（问题 9）

**问题描述：**
`_gitCacheMap` 和 `_memFilesCacheMap` 使用 FIFO 淘汰策略（按插入顺序删最旧的），而不是 LRU（删最久未访问的）。在 Gateway 长期运行场景下，活跃的 cwd 可能被淘汰，而失效的旧 cwd 占据缓存。

**修复方案：**
实现真正的 LRU：命中时将条目移到 Map 末尾（删除再重新插入）：
```typescript
if (cached && now - cached.ts < GIT_CACHE_TTL_MS) {
  // LRU：命中时将条目移到 Map 末尾
  _gitCacheMap.delete(key)
  _gitCacheMap.set(key, cached)
  return cached.result
}
```

**影响文件：**
- `src/core/ContextBuilder.ts`（`getGitContext` 和 `findMemoryFiles`）

### 6. 🟡 saveConfig 后 `_cachedMtime` 未同步（问题 12）

**问题描述：**
`saveConfig()` 更新 `_cachedConfig` 但未同步 `_cachedMtime`，导致下次 `loadConfig()` 因 mtime 不匹配触发不必要的重新读取。

**修复方案：**
在 `saveConfig()` 末尾同步 mtime：
```typescript
try {
  _cachedMtime = statSync(CONFIG_FILE).mtimeMs
} catch {
  _cachedMtime = 0
}
```

**影响文件：**
- `src/core/Config.ts`

---

### 7. 🟡 DSML 计数器全局状态 + delta 已发出无法撤回（问题 13 & 14）

**问题描述：**
- `_dsmlCallCounter` 是模块级全局变量，多会话共享计数器序列
- DeepSeek 模型输出 DSML 标记时，已发出的 `text_delta` 无法撤回，导致前端显示乱码

**修复方案：**
1. 将计数器改为实例级：`QueryEngine` 构造时创建 `_genDsmlId` 闭包
2. 对 DeepSeek 模型完全缓冲所有 delta，流结束后统一处理：
   - 解析到 DSML 工具调用 → 补发清理后的正文 delta
   - 无 DSML 标记 → 补发完整 fullText
   - 有 DSML 标记但解析失败 → 补发完整 fullText（保留原始内容）

**影响文件：**
- `src/core/QueryEngine.ts`

**验证方法：**
```bash
# 使用 DeepSeek 模型测试 DSML 工具调用
hrids-agent -m deepseek-chat --provider deepseek
# 发送需要工具调用的消息，观察前端是否显示 DSML 标记
```
